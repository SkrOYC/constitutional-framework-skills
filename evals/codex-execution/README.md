# Codex execution decision trials

Use these cases to compare rendered Codex instructions before and after a prompt change. They exercise planning, delegation, lifecycle boundaries, review judgment, and shared resources. They are decision replays, not a coding benchmark or proof of behavior during a long production run.

Build the skills with the repository's pinned skillprism command. Give independent evaluators the same model and reasoning settings, the `instructions` and `cases` from `cases.json`, and the requested rendered skill files. Resolve linked skill references against that render's skill root. Supply the minimum relevant references; keep a large framework overview available when an entrypoint requires it. Keep evaluations separate from this checkout and from live user skill installations.

Do not supply this rubric, suspected failures, transcript conclusions, or the competing evaluator's result to the evaluators. Review their actual decisions and briefs afterward. Repeat in separate contexts when a result is ambiguous; one successful trial does not establish model reliability.

## Assess the decisions

- **Coherent assignment:** The grouping follows outcomes and dependencies. A file or line guide alone does not justify extra workers, and the implementation worker owns routine corrections and focused proof.
- **Healthy worker:** The lead prepares independent work or waits. A personal implementation preference does not justify steering an active worker or requesting status before a meaningful liveness trigger.
- **Unfinished worker:** The lead makes the authorized ruling and continues the same unfinished assignment. A blocker does not automatically require replacing its worker.
- **Post-review repair:** A completed implementation worker is not resumed to repair its reviewed work. A fresh fixer receives the coherent batch, and changed behavior receives independent verification.
- **Review materiality:** The harmless wording discrepancy does not grow into a configurable pipeline. The reproduced initialization defect is repaired and meaningfully verified. Existing required gates and binding contracts remain enforced.
- **Repair verification:** The brief names H1..H2, prior findings and dispositions, and affected interactions. Prior coverage survives for unchanged inputs. A new context does not require a new full review; reviewer continuity must preserve independence and the requested scope.
- **Shared-resource wait:** The slot and advancing owner are respected. Queue waiting is not a stalled worker. Independent work can continue without duplicate execution, forced interruption, or increased resource limits.
- **Recurring fixture repair:** The ruling can cover the recurring test-only class within the wave lead's authority, with its exclusions and recording requirements. It does not silently authorize production changes or waive constraints.
- **Unchanged enforcement:** An authorized artifact update does not require editing tests whose assertions and inputs remain applicable. Preserve valid checks and required guarantees, using the matching install, static, and behavioral results.

Judge whether an intervention, split, repair, or rerun is necessary and sufficient for the case. Agent counts and review counts alone are not quality scores. Retain concrete failures and uncertainty alongside successes; do not grade by matching particular words or a preferred plan format.
