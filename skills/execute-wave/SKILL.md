# Execute wave

Read `references/framework-overview.md` before you start. This skill is the wave orchestrator, the **wave lead**: it sets the cross-epic path, binding plan constraints, lanes, merge order, and reconciliation, and epic leads execute inside those constraints. The wave lead never writes product code or edits constitution records; `reconcile` and `derive` do the latter, once. The CLI is `bun run ~/.{% if harness.id == "antigravity" %}gemini/antigravity-cli{% else %}{{ harness.id }}{% endif %}/skills/constitution-tooling/scripts/cli.ts <command> --root .`.

Planning lives here because only the wave lead sees every lane, the shared runtime, and the merge order at once. Keep its context lean: delegate substantial independent inspection to explorers that return conclusions rather than file dumps, do bounded reads yourself, and never take in epic leads' transcripts.

Resolve cross-epic decisions in Step 2. Plans delegate task authority but never grant sandbox, network, filesystem, or host permission; honor actual permission controls and report any denied action that blocks the authorized route.

{% if harness.id == "codex" %}A one-epic wave whose approved epic lead is Codex runs directly in this session after planning, with `single_epic_wave`, keeping merge and wave reconciliation duties. A Claude epic lead is dispatched through the bridge with `orchestrated` invocation, even for one lane, while this Codex session stays wave lead. Either way, milestones get fresh workers and independent reviewers.{% else %}A one-epic wave runs directly in this session as its epic lead after planning: record `single_epic_wave` and the caller in the plan, keep this skill's merge and wave reconciliation duties, and dispatch fresh milestone workers and independent reviewers, with no separate epic-lead session merely relaying the work.{% endif %}

## Inputs

- `tasks/critical-path.md`, freshly rendered: the wave table, the longest chain, and the out-of-band conflicts.
- The concurrency block in `constitution.yaml`: worktree layout, branch naming, merge strategy.
- The active epic files for the wave, and the tech-spec records, sidecars, recipes, flows, and glossary entries they cite.
- `reports/open-decisions.yaml`.
- The project's own agent instructions, for what the constitution doesn't carry: shared services and their lifecycle, locks, ports, per-lane setup, lane caps, mandatory manual verification. This skill is project-neutral; those rules reach the wave through the plan files and the hooks below, never through this file.
- The wave number from the user; without one, the lowest wave whose epics are all still active.
- What the user says about runtimes, models, the usage left on each, and each epic's difficulty. You propose the rest in the plan, which the user approves.

## Preflight

Run `render` and `validate`, and stop with a plain report if any check fails:

1. `validate` reports no errors.
2. Every epic in earlier waves is under `tasks/completed/`.
3. The wave's epics are pairwise scope-disjoint; `validate` enforces this, and the rendered table shows it.
4. When the project's instructions name a resource only one lane may hold at a time, at most one epic in the wave owns paths under it.
5. Every `pinned` contract an epic in the wave builds on is settled, present, or created by an earlier epic or by an epic in this wave that the others depend on. `validate` catches a pinned contract nobody creates; check the ordering yourself from the epic graph.
6. The default branch is clean and up to date; `gh auth status` succeeds.
7. The concurrency block names a merge strategy that matches an available merge skill (`merge-pr-rebase-delete` or `merge-pr-squash-delete`).
8. Inspect owner-required checks, which stay binding, and relevant runtime readiness. Test an unproven recipe's launch and doctor during preparation, without a full baseline suite by default. Record unavailable services and approved role fallbacks without inventing a hosted pass.

### Step 6: Merge in order

Merge each lane in the listed order as soon as it is eligible, while later lanes continue; don't wait for every Epic report, and never overtake an earlier lane without an authorized order change. Review completeness, ticket acceptance, and merge authorization are separate gates:

1. Record the reviewed base, merge base, and head from the final review result the Epic report references, and compute the stable patch id: `git diff <reviewed-merge-base> <reviewed-head> | git patch-id --stable`. Rebase the lane onto the current default branch, push through the project's permitted workflow, and compute the rebased diff's patch id. Finish this preparation before teardown or merge.
2. Assess the base delta as well as the patch. An unchanged patch id preserves unaffected patch-content judgments, not integration conclusions, because changed helpers, configuration, contracts, or runtime assumptions can affect path-disjoint lanes. If the base affects integration behavior or load-bearing verification assumptions, or those effects remain materially uncertain, require scoped independent verification of those interactions before merging; harmless base changes need no further reviewer or full panel. Run owner-required merge gates against the integration head; retained evidence keeps its historical verified-at commit.
3. If the patch changed, run a review-loop verification round scoped to that difference and its interactions. Either way, rerun only probes or measurements invalidated by changed behavior or relevant environment inputs; changed commit SHAs alone don't justify recapturing evidence. Record a passing rerun in the PR, and replace retained proof only when its acceptance observation changed. A failure is an Act-on finding assigned to the lane's lead, which owns evidence and closeout updates.
4. For a rebase conflict, assign one coherent conflict-resolution batch to a fresh fix worker with both epics' contracts as context, then review the resolved difference and run its affected gates. Record the conflict and resolution in the plan's Amendments section; a false disjointness claim routes to Stage 4.
5. Once the rebased candidate is review-clean and its required gates pass, perform the project's lane teardown: stop owned services, confirm recorded child processes exited, and remove only authorized scratch and local state. Branch deletion can remove a linked worktree, so finish every operation that needs its files first. Merge with the strategy named in the concurrency block, then advance to the next lane.

A failing owner-required gate, or an unavailable service that gate needs, blocks merging; unrelated optional hosted tests create no merge requirement. Use authorized alternatives and record unavailable proof honestly. If verification resumes after teardown, restore the owned runtime and tear it down again afterward.

After the last merge, confirm the default branch is clean, the wave branches are deleted, and the project's remaining runtime cleanup is complete.

### Step 7: Reconcile and derive once

On the default branch, run `reconcile` exactly once for the whole wave. It archives the epics, records actuals, settles records, appends proposed decisions and interim assumptions to the register, records fast-lane commits, writes the changelog entries, flips the verification commands and recipes that archived tickets owned, routes code decisions to Stage 3, renders, and commits. Then run `derive --write` and commit its changes as a second constitution-only commit; the order matters because reconcile refuses to run on a dirty tree. Never run either per epic.
