# Execute wave

Read `references/framework-overview.md` before you start. This skill is the wave orchestrator, the **wave lead**: it sets the cross-epic path, binding plan constraints, lanes, merge order, and reconciliation. Epic leads own execution inside those constraints. Workers and reviewers own their milestones. The wave lead never writes product code or edits constitution records; `reconcile` and `derive` do the latter once. The CLI is `bun run ~/.{% if harness.id == "antigravity" %}gemini/antigravity-cli{% else %}{{ harness.id }}{% endif %}/skills/constitution-tooling/scripts/cli.ts <command> --root .`.

The wave lead holds the highest perspective in the tree: it sees every lane, the shared runtime, and the merge order at once. That is why planning lives here. Keep its context lean: delegate substantial independent inspection to explorers that return conclusions, not file dumps; keep bounded reads with the planner, and the epic leads' transcripts never enter it.

Resolve cross-epic decisions in Step 2, then execute without routine approval pauses. Give concise progress updates and answer user steering. Plans delegate task authority; they never grant sandbox, network, filesystem, or host permission. Honor actual permission controls and report any denied action that blocks the authorized route.

{% if harness.id == "codex" %}For one epic whose approved epic-lead runtime is Codex, run directly after planning with `single_epic_wave`, retaining merge and wave reconciliation duties. If the approved epic lead uses Claude, keep this Codex session as wave lead and dispatch that lead through the bridge with `orchestrated` invocation, even for one lane. Preserve fresh milestone workers and independent reviewers in either topology.{% else %}For a wave containing one epic, run directly as the epic lead after planning. Record `single_epic_wave` and the caller in the plan, retain this skill's merge and wave reconciliation duties, and dispatch fresh milestone workers and independent reviewers. Don't add a separate epic-lead session merely to relay the same work.{% endif %}

## Inputs

- `tasks/critical-path.md`, freshly rendered: the wave table, the longest chain, and the out-of-band conflicts.
- The concurrency block in `constitution.yaml`: worktree layout, branch naming, merge strategy.
- The active epic files for the wave, and the tech-spec records, sidecars, recipes, flows, and glossary entries they cite.
- `reports/open-decisions.yaml`.
- The project's own agent instructions in the repository, for everything the constitution does not carry: shared services and their lifecycle, locks, ports, per-lane setup, lane caps, mandatory manual verification. This skill is project-neutral; those rules enter the wave through the plan files and the hooks below, never through this file.
- The wave number from the user. When none is given, take the lowest wave whose epics are all still active.
- What the user says about models and usage: which runtimes and models they want, how much usage is left on each, how hard each epic is. You propose the rest in the plan and the user approves it with the plan.

## Preflight

Run `render` and `validate`. Stop with a plain report if any check fails:

1. `validate` reports no errors.
2. Every epic in earlier waves is under `tasks/completed/`.
3. The wave's epics are pairwise scope-disjoint; `validate` enforces this, and the rendered table shows it.
4. When the project's instructions name a resource only one lane may hold at a time, at most one epic in the wave owns paths under it.
5. Every `pinned` contract an epic in the wave builds on is settled, present, or created by an epic in this wave that the others depend on or by an earlier one. `validate` catches a pinned contract nobody creates; check the ordering yourself from the epic graph.
6. The default branch is clean and up to date; `gh auth status` succeeds.
7. The concurrency block names a merge strategy that matches an available merge skill (`merge-pr-rebase-delete` or `merge-pr-squash-delete`).
8. Inspect owner-required checks and relevant runtime readiness. Test an unproven recipe's launch and doctor during preparation; don't add a full baseline suite by default. Record unavailable services and approved role fallbacks without inventing a hosted pass. Private-project verification runs locally unless the owner needs remote tests. Contribution CI is appropriate by default for projects accepting outside contributions; visibility alone doesn't establish that model. Keep test workflows separate from authentication, signing, publishing, deployment, and release execution. Existing owner-required gates remain binding.

### Step 6: Merge in order

As soon as the next lane in the listed merge order is eligible, integrate it while later lanes continue. Don't wait for every Epic report. Never overtake an earlier lane without an authorized order change. Review completeness, ticket acceptance, and merge authorization are separate gates:

1. Record the reviewed base, merge base, and head from the final review result referenced by the Epic report. Compute the stable patch id: `git diff <reviewed-merge-base> <reviewed-head> | git patch-id --stable`. Rebase the lane onto the current default branch, push through the project's permitted workflow, and compute the rebased diff's patch id. Finish this preparation before teardown or merge.
2. Assess the base delta as well as the patch. An unchanged patch id preserves unaffected patch-content judgments, not integration conclusions. Changed helpers, configuration, contracts, or runtime assumptions can affect path-disjoint lanes. If the base affects integration behavior or load-bearing verification assumptions, or those effects remain materially uncertain, require scoped independent verification of those interactions before merging. Harmless base changes don't require another reviewer or full panel. Run owner-required merge gates against the integration head; retained evidence keeps its historical verified-at commit.
3. If the patch changed, run a review-loop verification round scoped to that difference and its interactions. In either case, rerun only probes or measurements invalidated by changed behavior or relevant environment inputs. Record a passing rerun in the PR; replace retained proof only when its acceptance observation changed. Don't recapture evidence merely because commit SHAs changed. A failure is an Act-on finding assigned to the lane's lead, which owns evidence and closeout updates.
4. For a rebase conflict, assign one coherent conflict-resolution batch to a fresh fix worker with both epics' contracts as context. Review the resolved difference and run its affected gates. Record the conflict and resolution in the plan's Amendments section; a false disjointness claim routes to Stage 4.
5. Once the rebased candidate is review-clean and its required gates pass, perform the project's lane teardown. Stop owned services, confirm recorded child processes exited, and remove only authorized scratch and local state. Branch deletion can remove a linked worktree, so finish every operation that needs its files first. Merge with the strategy named in the concurrency block, then advance to the next lane.

A failing owner-required gate or unavailable service needed for that gate blocks merging. Unrelated optional hosted tests don't create a merge requirement. Use authorized alternatives and record unavailable proof honestly. If verification resumes after teardown, restore the owned runtime and tear it down again afterward.

After the last merge, confirm the default branch is clean, the wave branches are deleted, and the project's remaining runtime cleanup is complete.

### Step 7: Reconcile and derive once

On the default branch, run `reconcile` exactly once for the whole wave. It archives the epics, records actuals, settles records, appends proposed decisions and interim assumptions to the register, records fast-lane commits, writes the changelog entries, flips verification commands and recipes archived tickets owned, routes code decisions to Stage 3, renders, and commits. Then run `derive --write`, and commit what it changed as a second constitution-only commit; reconcile refuses to run on a dirty tree, so the order matters. Do not run either per epic.
